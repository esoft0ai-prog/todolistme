# Finora security & privacy

Finora handles sensitive financial data and is designed so that **nothing leaves the phone unless the user explicitly exports it**.

## Local security architecture

| Asset | Protection |
|---|---|
| Financial database (`finora.db`) | SQLCipher AES-256 encryption at rest. Key: 32 bytes from the platform CSPRNG (`expo-crypto`), stored with `expo-secure-store` (encrypted by a key in the Android Keystore, hardware-backed where available). Stored in app-private storage (`/data/data/com.finora.app/`), inaccessible to other apps. `PRAGMA secure_delete = ON` overwrites deleted content. |
| App-lock PIN | Never stored. `pbkdf2-sha256$10000$<16-byte random salt>$<32-byte hash>$<length>` kept in Keystore-backed secure storage. Constant-time comparison. |
| Brute-force protection | Failure counter and lock-until timestamp persisted in secure storage (killing the app does not reset them). 5 free attempts, then 30 s lock doubling per further failure up to 1 hour. Partial PINs are never auto-submitted. |
| Biometrics | `expo-local-authentication` (`USE_BIOMETRIC`); device-credential fallback disabled — Finora's own PIN is the fallback. |
| Screen contents | Lock screen covers the navigator and hides it from accessibility services; Android back on the lock screen leaves the app. `FLAG_SECURE` (default on) blocks screenshots/screen recording and blanks the app in Recents. Auto-lock after a configurable background timeout (immediately … 15 min). |
| Backups made by the user | Plain JSON (so it can be restored anywhere) with a SHA-256 integrity checksum. Users are told to store them safely. Encrypted/password-protected backup files are on the roadmap. |
| Android backup / device transfer | `allowBackup="false"`, `fullBackupContent="false"`, and `dataExtractionRules` excluding every domain for both cloud backup and device-to-device transfer. |

## Network & privacy

* **Release builds have no `INTERNET`, `ACCESS_NETWORK_STATE` or `ACCESS_WIFI_STATE` permission** (removed by a release-only manifest overlay generated by `plugins/withFinoraAndroid.js`). Android therefore enforces that the app cannot send data anywhere.
* No analytics, crash reporting, ads, tracking or remote config SDKs. `expo-updates` is not included.
* expo-notifications' Firebase messaging service is removed from the manifest; only local notifications are used; push-token registration is never enabled.
* Explicitly blocked permissions: location (fine/coarse/background), camera, microphone, contacts, SMS, call log, phone state, external storage/media, overlay, advertising ID, C2DM.
* Also blocked: launcher-badge permissions merged by the notification library (Samsung, Huawei, Oppo, HTC, Sony…) and the Play install-referrer permission — Finora sets no badges and is not distributed through Play.
* Remaining permissions: `POST_NOTIFICATIONS`, `RECEIVE_BOOT_COMPLETED` (re-arm reminders after restart), `SCHEDULE_EXACT_ALARM` (≤ Android 12L) / `USE_EXACT_ALARM` (reminders on time), `VIBRATE`, `USE_BIOMETRIC`/`USE_FINGERPRINT`. Debug builds additionally have `INTERNET` for the Metro dev server.
* Files are saved/shared with the Storage Access Framework and share sheet — no storage permission.

## Security review (performed during development)

| Area | Finding | Resolution |
|---|---|---|
| Insecure storage | PIN or DB key in plain preferences would be readable on rooted devices / backups. | Both live only in Keystore-backed secure storage; PIN only as salted PBKDF2 hash; DB encrypted. |
| Hard-coded secrets | Signing credentials in `build.gradle` would leak with the repo. | Release signing reads `android/keystore.properties` or `FINORA_*` env vars; `keystore.properties` and `*.keystore` are git-ignored. No API keys exist. |
| Unnecessary permissions | Libraries merge extra permissions (e.g. storage, AD_ID, INTERNET). | `blockedPermissions` + release overlay; merged manifest inspected after build (see BUILD_ANDROID.md). |
| Data leakage | Android auto-backup and D2D transfer could copy data off-device; screenshots/recents thumbnails expose balances; notifications on the lock screen. | Backup/transfer disabled; `FLAG_SECURE`; notification channels use `PRIVATE` lock-screen visibility. |
| SQL injection | User text in LIKE searches and dynamic backup columns. | All values bound as parameters; LIKE wildcards escaped with `ESCAPE '\'`; column names come only from the static `BACKUP_TABLES` whitelist; `IN (...)` lists built from placeholders. Tested with `'; DROP TABLE …` inputs. |
| Unsafe file handling | Oversized/malicious import files; spreadsheet formula injection in CSV; script injection in the HTML report. | 50 MB limit; JSON parsed defensively; every row sanitised (types, enums, dates, lengths); CSV cells starting with `= + - @ tab CR` are prefixed with `'`; HTML report escapes all user text and sets a `default-src 'none'` CSP. |
| Backup manipulation | Edited backup could inject inconsistent data or unknown columns. | Checksum mismatch warns and requires explicit confirmation; unknown columns dropped; references validated; DB `CHECK`/`FOREIGN KEY` constraints enforced; the whole restore is one transaction with `PRAGMA foreign_key_check`, rolled back on any error. Safety snapshot written before restore. |
| Weak validation | Negative/zero amounts, invalid dates, over-repayment. | Shared validators in `domain/validation.ts` + service-level checks + DB constraints (defence in depth). |
| Authentication bypass | Killing the app to reset attempts; restoring a backup that turns on app lock without a PIN; navigator reachable under the lock screen; back button. | Persistent lockout; security preferences are device-local and never restored; navigator hidden from accessibility while locked, lock overlay captures all touches; back button exits. Auto-lock on resume uses the time spent in background. |
| Denial of service by data | Huge reminder counts could exhaust Android's 500-alarm limit. | Planner horizon 120 days, hard cap 200 scheduled notifications. |
